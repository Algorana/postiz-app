# Спецификация: скрытие неиспользуемых frontend-функций

## Цель

Скрыть неиспользуемые функции Postiz только на фронте, без удаления бизнес-логики, backend/API, shared-модулей и существующих данных.

Ключевой принцип: **скрыть, а не удалить**. В местах отключения должны использоваться короткие комментарии с маркером `HIDDEN`, а подробная инструкция восстановления должна быть вынесена в `hided/README.md`.

## Область изменений

Изменения затрагивают только frontend-приложение `apps/frontend` и документацию восстановления `hided/`.

Backend, orchestrator, database, API contracts и shared provider-логика не изменяются.

## Требования к скрытию в сайдбаре

### Что скрыть

Из основного sidebar/top menu нужно скрыть следующие пункты:

- `Agent` → `/agents`;
- `Analytics` → `/analytics`;
- `Plugs` → `/plugs`;
- `Integrations` → `/third-party`.

Важно: под `Integrations` имеется в виду именно пункт меню `/third-party`. OAuth/callback роуты `/integrations/social/...` трогать нельзя, так как они нужны для подключения разрешённых провайдеров.

### Поведение UI

- Скрытые пункты полностью исчезают из меню.
- Оставшиеся пункты должны схлопнуться без плейсхолдеров, disabled-состояний или визуальных заглушек.
- Скрытие применяется для всех ролей и всех пользователей: `USER`, `ADMIN`, `SUPERADMIN`, self-hosted/general режимы.

### Прямые URL

Для скрытых страниц прямое открытие должно давать настоящий frontend 404 через `notFound()`:

- `/agents`;
- `/agents/[id]`;
- `/analytics`;
- `/plugs`;
- `/third-party`.

Не нужно делать redirect на календарь и не нужно показывать пустой компонент с текстом disabled/hidden.

## Требования к списку провайдеров

### Что оставить

В основном сценарии `Add Channel` нужно показывать только:

- TikTok, identifier: `tiktok`;
- Instagram Standalone, identifier: `instagram-standalone`.

Все остальные провайдеры скрываются из основного модального окна добавления канала.

### Где применять ограничение

Ограничение применяется **только к основному Add Channel flow**.

Не требуется распространять это ограничение на:

- onboarding flow;
- mobile integrations flow;
- invite-link flow;
- reconnect/refresh существующих integrations;
- выбор уже подключённых каналов при создании/редактировании постов.

### Уже подключённые интеграции

Существующие подключённые интеграции других провайдеров не скрывать и не удалять. Они должны остаться видимыми и доступными там, где пользователь уже работает с подключёнными каналами: календарь, создание/редактирование постов, существующие списки integrations.

## Требования к аналитике/статистике в календаре

### Что скрыть

В карточках календаря нужно убрать кнопку/иконку `Statistics` целиком.

Текущее поведение находится в `CalendarItem`: кнопка показывается в hover-actions и открывает `StatisticsModal`, где есть Post Analytics и Short Links Statistics. По требованию нужно скрыть именно кнопку входа из календарной карточки.

### Где скрывать

Кнопка статистики/аналитики не должна появляться ни в одной карточке календаря:

- list view;
- day view;
- week view;
- month view;
- опубликованные, запланированные, draft/error/missing-release карточки — везде, где используется `CalendarItem`.

### Что не удалять

- Не удалять сам `StatisticsModal`.
- Не удалять backend/API аналитики.
- Не удалять компоненты статистики и графиков.
- Допустимо убрать или адаптировать неиспользуемые props/imports, если иначе будут lint/type/build ошибки.

## Требования к 404 для скрытых страниц

Для route-файлов скрытых страниц допустимо заменить содержимое страницы на вызов `notFound()` из Next.js.

При этом старое поведение должно быть восстановимо по документации в `hided/README.md`. В коде рядом с отключением использовать короткий комментарий формата:

```ts
// HIDDEN: unused feature, see hided/README.md
```

или аналогичный краткий маркер.

## Документация восстановления

Нужно создать папку:

```text
hided/
```

и файл:

```text
hided/README.md
```

README должен содержать:

1. список всех скрытых функций;
2. список файлов/компонентов, где они скрыты;
3. краткую причину скрытия;
4. чеклист восстановления;
5. предупреждение, что OAuth `/integrations/social/...` не относится к скрытому пункту `/third-party` и не должен отключаться.

## Подход к коду

Пользователь выбрал подход: отключать/скрывать через комментарии и явные UI-изменения, а не через полноценную feature-flag систему.

Требования к стилю реализации:

- использовать короткие комментарии `HIDDEN` рядом с отключёнными блоками;
- не оставлять код, который ломает TypeScript/lint;
- не добавлять новые зависимости;
- не менять backend;
- не менять provider identifiers;
- не трогать существующие данные и подключённые integrations;
- не делать disabled-состояния вместо скрытия.

## Риски и компромиссы

### Комментирование вместо feature flag

Плюсы:

- быстро;
- явно видно, что скрыто;
- просто восстановить вручную.

Минусы:

- менее гибко, чем env/feature flag;
- требует ручного изменения кода для включения функций обратно;
- может быть сложнее поддерживать при будущих изменениях upstream.

### 404 для существующих routes

Плюсы:

- прямые ссылки на скрытые функции не открывают UI;
- поведение соответствует требованию «реальный 404».

Минусы:

- при восстановлении нужно вернуть содержимое route-файлов;
- если какие-то внутренние ссылки останутся, пользователь увидит 404.

### Ограничение providers только в Add Channel

Плюсы:

- не ломает существующие integrations и старые workflow;
- не затрагивает onboarding/mobile/invite/reconnect без явной необходимости.

Минусы:

- другие frontend entry points теоретически могут показать больше провайдеров, если пользователь попадёт туда обходным путём.

## Планируемые изменения по файлам и модулям

### Sidebar/menu

Файл:

- `apps/frontend/src/components/layout/top.menu.tsx`

План:

- скрыть пункты `Agent`, `Analytics`, `Plugs`, `Integrations`;
- использовать краткий комментарий `HIDDEN`;
- оставить остальные пункты меню без плейсхолдеров.

### Hidden routes / 404

Файлы:

- `apps/frontend/src/app/(app)/(site)/analytics/page.tsx`;
- `apps/frontend/src/app/(app)/(site)/plugs/page.tsx`;
- `apps/frontend/src/app/(app)/(site)/third-party/page.tsx`;
- `apps/frontend/src/app/(app)/(site)/agents/page.tsx`;
- `apps/frontend/src/app/(app)/(site)/agents/[id]/page.tsx`;
- возможно `apps/frontend/src/app/(app)/(site)/agents/layout.tsx`, если layout продолжит показывать UI или мешать 404.

План:

- заменить доступ к скрытой функциональности на `notFound()`;
- не трогать `/integrations/social/[provider]/page.tsx` и related OAuth layout.

### Providers in Add Channel

Файл:

- `apps/frontend/src/components/launches/add.provider.component.tsx`

План:

- в основном Add Channel flow отфильтровать `social` до `tiktok` и `instagram-standalone`;
- не применять это ограничение к invite/onboarding/mobile, если они используют тот же компонент с соответствующими props;
- сохранить возможность восстановления через `hided/README.md`.

### Calendar card analytics/statistics button

Файл:

- `apps/frontend/src/components/launches/calendar.tsx`

План:

- скрыть hover-action `Statistics` в `CalendarItem` для всех состояний и всех view;
- оставить `StatisticsModal` и связанный код в проекте;
- убрать или адаптировать неиспользуемые props/imports только если это необходимо для корректной сборки.

### Документация

Файл:

- `hided/README.md`

План:

- описать скрытые пункты;
- указать файлы;
- добавить checklist восстановления;
- отдельно указать, что `/integrations/social/...` не скрывался.

## Проверки

Пользователь явно указал, что обязательные проверки в рамках этой задачи не нужны.

Тем не менее при реализации желательно не оставлять очевидных TypeScript/lint ошибок из-за неиспользуемых imports/props.
